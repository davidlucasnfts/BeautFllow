Proposta — Fechar o ciclo de consentimento

16/10/2026 · Aguardando autorização · Nenhum código alterado

Constatação da análise: os modelos de termos (entregue hoje) resolvem a criação, mas o ciclo completo é: criar termo → apresentar ao cliente → coletar assinatura → alerta zera. Hoje só a primeira etapa existe. A ponta de assinatura está morta no código.

O que a análise encontrou (baseado no código real)

Gap 1 — Alerta LGPD do Dashboard nunca zera. O cliente é cadastrado com consentGiven = false e nenhum código no projeto inteiro jamais grava esse campo como true (grep global confirmou). Ou seja: todo cliente entra "pendente", o alerta "N clientes não assinaram a LGPD" é permanente e o botão "Resolver" leva para a página de gestão de termos — onde não existe ação que resolva.
Gap 2 — Backend de assinatura pronto, sem tela. Os endpoints consent.sign e consent.signaturesByClient existem no backend (com audit log, IP, user-agent), mas nenhum componente os chama. Não existe modal de assinatura em lugar nenhum — a ficha do cliente não mostra quais termos ele assinou.
Gap 3 — Agendamento público (/agendar/:slug) sem consentimento. O cliente final preenche nome + WhatsApp e agenda, mas não aceita nada sobre LGPD. Clientes vindos do link entram sempre pendentes — justamente os que o salão quase nunca vê pessoalmente.
Gap 4 — services.requiresConsent é decorativo. O flag existe no cadastro de serviço e aparece no card, mas não é verificado em nenhum fluxo de agendamento (nem público, nem interno).

Proposta — 4 entregas pra fechar o ciclo RECOMENDADA

1. Checkbox LGPD no cadastro de cliente + edição

No diálogo "Novo cliente" e na edição: checkbox "Cliente autoriza o uso dos dados (LGPD)" marcado → grava consentGiven = true + consentGivenAt. Zero migration — usa colunas que já existem. A badge "Dados autorizados" passa a funcionar de verdade.

2. Checkbox de aceite obrigatório no agendamento público

Em /agendar/:slug, antes de confirmar: checkbox obrigatório "Aceito o uso dos meus dados para agendamento, conforme a política do estabelecimento". Se o cliente é novo, entra cadastrado com consentGiven = true; se já existia, atualiza. Resolve o Gap 3.

3. Coleta de assinatura de termo na ficha do cliente

Na ficha expandida do cliente, nova seção "Termos assinados": lista os termos ativos do salão com status (assinado/não) via signaturesByClient + botão "Registrar assinatura" → modal exibe o texto do termo, o atendente confirma verbalmente e clica em confirmar → chama consent.sign (grava data/hora + usuário logado como responsável). Ativa o backend que já está pronto — aí os 4 modelos de termo entregues hoje passam a ter utilidade real.

4. Aviso de serviço que exige termo (requiresConsent) + destino do botão "Resolver"

Ao criar/editar agendamento interno de serviço com requiresConsent = true para cliente sem assinatura: banner âmbar "serviço exige termo assinado" com atalho pra coletar (não bloqueia — só alerta, padrão MVP). E o botão "Resolver" do Dashboard passa a levar para a lista de clientes pendentes, onde a entrega 1 resolve em 1 clique.

  • Prós: ciclo completo fecha; alerta do Dashboard zera e passa a significar algo; os 4 modelos de termo ganham uso real; agendamento por link fica aderente à LGPD; tudo com colunas/endpoints que já existem (no máximo 1 migration pequena se quisermos marcar o termo-LGPD padrão — evitável no MVP)
  • Contras: a assinatura via modal é "confirmada pelo atendente" (assinatura digital desenhada fica pra uma fase futura); o termo assinado no app não é gerado como PDF

Esforço: médio — 4 telas/componentes tocados, nenhuma migration obrigatória, backend quase todo pronto.

Minha recomendação: implementar as 4 entregas juntas — sozinha, a biblioteca de modelos (entregue hoje) fica inútil, porque o termo criado não pode ser apresentado a ninguém.

Me diz: "pode fazer" que implemento as 4; ou escolhe um recorte (ex: "só 1 e 2" pra resolver o alerta do Dashboard); ou "não faz nada" se preferir manter como está.
